### Модуль 1 — база данных (50 мин)

1. pgAdmin → Databases → Create → Database → `chudo_obuv`.
2. Query Tool → выполнить `database/schema.sql` (F5).
3. Положить xlsx в папку `import/`, в `config.py` указать пароль, выполнить
   `python database/import_data.py` (создаёт таблицы и грузит данные).
4. ER-диаграмма: правой кнопкой на базе → **ERD For Database** → расставить таблицы →
   экспорт картинки → сохранить как **`ERD_module_1.pdf`** (через «Печать в PDF»).
   Готовый пример — `database/ERD_module_1.pdf`.
5. Скрипт БД с данными: правой кнопкой на базе → **Backup…** → Format **Plain**,
   в Data Options включить **Use INSERT commands** (иначе будет `COPY`, который не
   выполняется в Query Tool) → `chudo_obuv_dump.sql`. Или в консоли:
   `pg_dump -U postgres -d chudo_obuv --clean --if-exists --column-inserts -f chudo_obuv_dump.sql`
6. «Автотест» → Модуль 1 → нужные задания → скопировать контрольные суммы.

**Ловушки в данных заказчика (импорт их уже обрабатывает):**

- Размеры бывают половинные (`36.5`) → тип размера `NUMERIC`, не `INTEGER`.
- В Products_import у модели «Туфли женские … с металлическими вставками» стоит
  **неразрывный пробел** — по названию она не совпадает с остатками и заказами.
  Решение: заменять `\xa0` на обычный пробел и схлопывать пробелы.
- В остатках и заказах название **сокращено**: «Черные туфли в классическом стиле»,
  а в каталоге «Черные туфли в классическом стиле — база для деловых образов».
  Решение: искать модель того же производителя, название которой начинается с указанного.
- Номер заказа из файла сохраняется как `order_id`; после импорта нужно сдвинуть
  последовательность (`setval`), иначе новый заказ из приложения получит занятый номер.

## 3. Теоретические задания модуля 1 — мой разбор

> Это рассуждения по нашей ER-диаграмме, а не официальные ответы. Перепроверь логику на экзамене.

**1.2 (функции ↔ файлы):** 1 — Products, 2 — Sizes, 3 — Stock_Items, 4 — Orders, 5 — Users.
- А (количество товарных позиций: модель + размер) → 1, 2, 3
- Б (изображение модели) → 1
- В (клиент выбирает пары доступного размера и модели) → 1, 2, 3
- Г (список заказов: дата, ФИО клиента) → 4, 5
- Д (управление заказами) → 3, 4, 5 (заказ меняет остатки товарных позиций)

**1.4 (неподходящие схемы):** **1, 2, 4, 5, 6**. Подходит только 3: роли, пользователи,
модели, размеры, товарные позиции, заказы и состав заказа хранятся раздельно.
(1 и 5 — всё в одной таблице; 2 — размер и количество внутри товара, нет состава заказа;
4 — нет товаров/размеров, название и размер дублируются в составе; 6 — нет ролей,
товарных позиций и цены в составе заказа.)

**1.5 (типы):** А — INTEGER, Б — VARCHAR, В — VARCHAR, Г — DATE, Д — VARCHAR,
Е — VARCHAR, Ж — NUMERIC (есть 36.5), З — INTEGER, И — NUMERIC, К — INTEGER,
Л — NUMERIC, М — INTEGER.

## 4. Вопросы, которые могут задать эксперты

- **Почему 3НФ?** Каждый факт хранится один раз: категория, производитель, роль, размер —
  в справочниках; количество — в товарной позиции (модель+размер); цена продажи — в составе
  заказа (она могла измениться после заказа, поэтому не берётся из `products`).
- **Зачем `ON DELETE CASCADE` у `order_items`?** Удаление заказа удаляет его состав —
  нет «осиротевших» строк. А модель, которая есть в заказах, удалить нельзя (`RESTRICT`).
- **Как считается скидка?** Берём период от 1-го числа прошлого месяца до 1-го числа
  текущего (правая граница не включается). Если у модели нет заказов в этом периоде —
  цена × 0,75. Код — `app/discount.py`.
- **Почему поиск в Python, а не `ILIKE`?** `casefold()` гарантированно работает с кириллицей
  при любой локали базы.
- **Что если два менеджера оформят заказ на последнюю пару?** `SELECT … FOR UPDATE`
  блокирует строку остатка в транзакции, второй получит сообщение «осталось 0 шт.».
